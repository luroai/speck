0.6.0 is a minor release that lets you see and change speck's settings from the panel, choose the models that build and review your tickets, and keep shipping when `main` fails or has moved on.

## What matters most

- **A Settings view in the panel.** Before, the only way to know what a setting did was to read the comments in `speck/config.yml`, and the only way to change one was to edit the file. Now the panel's Settings button opens a view of the settings people tune, each with its value and an "i" button that explains what it does and what changing it would mean. You can change them there and save them all with one button. Switching `auto_ship` on, or letting it cover another risk, first names the tickets that would then ship without you, and nothing changes until you say yes.
- **Settings for this machine only.** `speck config set --machine max_parallel_builds 3` sets how many builds this computer keeps going without changing the project's shared settings, so a small laptop and a bigger machine can work on the same project at their own pace. `max_parallel_tests` works the same way, and the Settings view can set both for this machine too.
- **Choose the models.** The new `builder_model` setting picks the model Claude Code builds your tickets on. The Settings view lists the models the reviewer offers, Codex's or Claude's, so you pick one instead of typing its exact name. A Claude build can now have a Claude reviewer without `allow_same_model_review`, as long as the two models are both chosen and differ.
- **Setup goes through the settings that matter.** Setting speck up now explains `auto_ship`, how much runs at once and the ticket size limits in the same words as the Settings view, recommends a value for each and asks. It turns on shipping without you only if you say yes to that setting by itself. `speck config show` lists the same settings and explanations in your terminal.
- **Shipping copes better.** An approved fix ticket ships while shipping is paused for a failing `main`, so the fix doesn't wait for you. A ticket that breaks tests that pass on `main` is handed back to its build to fix, rather than `main` being blamed. And when someone has changed `main` on GitHub while your own `main` has commits of its own, `speck ship` merges GitHub's in and carries on instead of stopping overnight.
- **Builds catch broken project rules sooner.** The new `commands.checks` setting lists quick test files that check rules for the whole repo. Every build runs them before each review round, so a build that breaks one finds out straight away rather than when it ships.
- **Documents can be reworded freely.** A criterion about how a document reads is now checked by the reviewer, not pinned by a test, so editing a README or the docs by hand no longer fails the tests and holds up every ship.

## Install

Paste the setup prompt from the README into your coding agent, or run this in your project's folder:

```sh
npx github:luroai/speck#v0.6.0 init
```

## Upgrading from 0.5.4

- Run `npx github:luroai/speck#v0.6.0 init` in your project to update the speck command and skills. It keeps your config and tickets.
- Two new settings can go in `speck/config.yml`, and each defaults to how speck worked before: `builder_model` (blank: Claude Code's own default model) and `commands.checks` (blank: no extra checks). Values for this machine only, set with `speck config set --machine`, are kept in `speck/.cache/machine/config.yml`, which git ignores; with none set, the shared values apply as before.
- If your builder and reviewer are the same agent and you'd rather not set `allow_same_model_review: true`, set `builder_model` and `reviewer_model` to two different models instead.
- A `speck run` that's already on is still running its old code until it switches by itself once it's idle, as 0.5.3 made it do.

See everything that's changed in the [0.6.0 section of the changelog](https://github.com/luroai/speck/blob/v0.6.0/CHANGELOG.md#060--18-october-2026).
