1.4.0 is a minor release about less waiting. Tickets used to queue behind each other whenever they might touch the same file, a waiting ticket couldn't start until the one before it had shipped, and builds re-ran tests and re-read work they had already checked. Now tickets wait only when one needs the other's work, a ticket can start on the approved work of the one it waits for, and builds and reviews skip what hasn't changed. speck also stops less often to ask you, and you can set several tickets ready at once.

## What's new

- **Tickets wait only when they must.** `/speck-ticket` chains a ticket after another only when it needs something the other makes, or both would rewrite the same lines. Tickets that merely touch the same file build side by side, and when it's unsure it names the shared file so you can chain them. So more of your ready tickets build at once.
- **Start on approved work.** `speck start`, and `speck run` by itself, start a ticket as soon as the one ticket it still waits for is approved, on top of that ticket's work. Its reviews and size count look only at its own change, and it ships after the other. So a waiting ticket doesn't sit idle while the one before it waits to ship.
- **Merge rounds read only what changed.** When an approved ticket has to merge newer work in, the reviewer sees how the clash was settled and anything changed since it approved, not the whole ticket again. So tickets that bump into other work get back to shipping faster.
- **Fewer test re-runs.** A failing related test run ends with the command to run only the files that failed and the build's own, and a passing run of the same tests on the same code is reused instead of run again. An idle `speck run` reads only the tickets that have changed. So builds spend less time waiting for test turns, and speck uses less of the machine.
- **Test turns across your projects.** `speck config set machine_parallel_tests <n>` caps how many test runs go at once across every project on your machine. So tests that fail only on a busy machine fail less.
- **Checks speck can't make wait for you at the end.** With `watch: decide`, when a build asks for a check in the app that speck can't make, such as how something sounds, it goes with the build's recommendation and lets the build finish. The approved ticket then waits for you, with the check listed in its review pack. So you look once, at the end, instead of the build stopping halfway.
- **Answering at the review limit works.** When a build runs out of review rounds and you answer its question, the ticket gets 2 more rounds instead of blocking again straight away. speck never answers that question for you. So letting a build try again does what you meant.
- **Set several tickets ready at once.** `speck set <id> <id>… status ready` checks and sets each one, leaves any that aren't ready, and tells you why. So Gate 1 after a round of ticket writing takes one command.

The shipped price table has this release's rates. Costs speck works out from tokens are still estimates at API list prices, so they can differ a little from what you were billed.

## Update

Paste the setup prompt from the README into your coding agent, or run this in each project's folder:

```sh
npx github:luroai/speck#v1.4.0 init
```

## Upgrading from 1.3.1

- Run `npx github:luroai/speck#v1.4.0 init` again in each project to update the speck command and skills. It keeps your config and tickets.
- There are no new settings in `speck/config.yml`. `machine_parallel_tests` is optional and lives in `~/.config/speck/config.yml`, for every project on the machine. Until you set it, test runs are limited only by each project's `max_parallel_tests`, as in 1.3.1.
- `speck run` may now start a ticket before every ticket in its `after:` list has shipped, when all but one have and that one is approved. It still ships them in order.
- `/speck-ticket` adds fewer `after:` links, so two tickets touching the same file may build at once and meet at ship. speck merges and re-reviews them as before.
- With `watch: decide`, a low-risk approved ticket may now wait for you with a check left in its review pack, rather than its build stopping with a question.
- Answering a question at the review limit now allows 2 more review rounds. `limits.max_review_rounds` is unchanged, and speck no longer takes the recommendation of such a question by itself.

See everything that's changed in the [1.4.0 section of the changelog](https://github.com/luroai/speck/blob/v1.4.0/CHANGELOG.md#140--15-november-2026).
