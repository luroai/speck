# speck — product brief

Status: 0.14.0, a public preview · 23 October 2026

## Thesis

**You own two decisions: what gets built and what gets shipped. Everything in between is automated.**

PMs have practised spec-driven development for years. It's called a PRD, and it reaches engineers as a ticket. speck applies the same workflow to AI coding agents. You write, or approve, a small ticket. One agent builds it. A second, independent agent reviews it until it's good enough. Then you ship it.

OpenSpec showed the value of keeping specs in the repo. speck keeps that idea but swaps the ceremony for small tickets and an adversarial review loop. There is no separate spec to keep up to date: the code, the tickets and the tests are the record of what the product does.

## Who it's for

- **Primary:** product-minded builders, such as PMs and founders, who can write a good ticket but don't want to review code line by line, and who want to ship personal or small-team projects quickly without giving up quality. They're comfortable setting speck up through a conversation with their agent and running it on their own machine.
- **Secondary:** engineers who want a lightweight, auditable loop of ticket, agent build, independent review and merge.
- **Where it's heading:** people who'd rather not have a development setup at all. That needs speck hosted, with builds running in the cloud, which is a deliberate later step (see "Where it's heading" below).
- **Not for:** large multi-team specification, or work that needs design documents spanning many changes. Use OpenSpec or similar for that.

## Principles

1. **The repo is the source of truth.** Ideas, tickets and review transcripts are Markdown files in the repo, beside the code they describe. Any tool, including the panel, reads and writes these files and nothing else.
2. **Small tickets only.** A ticket is one agent, one sitting, one branch. If a ticket is too big for that, it gets split. It never gets stretched.
3. **Review is adversarial and independent by default.** The builder never reviews its own work. A separate reviewer, preferably a different model, must approve it.
4. **Humans hold two gates.** Gate 1 is moving a ticket to `ready`. Gate 2 is shipping it with `/speck-ship`, or the Ship button in an approved ticket's review pack in the panel, which merges it. Agents never merge or ship unless the user runs `/speck-ship` or clicks that Ship button, and never click it themselves. The one exception is auto-ship: if you set `auto_ship: true` in `speck/config.yml`, `speck run` ships each approved ticket whose risk is listed in `auto_ship_risk`, one at a time. It's off by default. A document task never ships by itself, whatever `auto_ship` says: reading the document is its review, so it waits for you. How a ticket ships is `ship_mode`: `local`, the default, merges it into the base branch on your machine and pushes it, and `pr` opens a GitHub pull request for each approved ticket, with its review pack, so that shipping merges the pull request on GitHub and nothing is pushed straight to the base branch (see `speck pr`). Either way, shipping is still Gate 2.
5. **Evidence over trust.** Every approved ticket has a review pack (`speck pack <id>`) that a non-coder can judge: each acceptance criterion with its result, a plain-English change summary, and flagged risks.
6. **Measure actuals.** Every ticket records its review rounds, time and the reviewer's tokens, and builds that `speck run` starts record the builder's tokens and cost. That data is the product's proof.
7. **One build at a time.** speck runs one build at a time (WIP 1) unless you change it, each in its own worktree, so you keep shaping ideas and tickets on the base branch while builds and ships are handled. You can create tickets, set them ready and walk away. Builds end at approved, and one ship queue in `speck run` ships tickets one at a time, handing a ticket back to its build only when the ship needs work on it. `max_parallel_builds` in `speck/config.yml` sets how many builds `speck run` keeps going at once: 1 unless you change it. Why:
   - **Your attention is the bottleneck.** speck's value is its gates, and what limits it is your attention, not agent time.
   - **It keeps things simple.** Each build starts from the latest base branch, so order, `after:` dependencies, conflicts and a broken base branch stay simple.
   - **It fits speck's users.** They shape product rather than debug races.
   - **Isolation isn't parallelism.** speck keeps worktrees for isolation, so a build never touches your checkout. Running builds side by side is a different thing.
   - **The cost is throughput.** At the default, tickets are built one after another.
   - **One build at a time is the default, not a limit.** Raising `max_parallel_builds` in `speck/config.yml` is supported: `speck run` then keeps that many going at once, while its ship queue still ships tickets one at a time.

## The workflow

```
idea / conversation
  → /speck-capture        → speck/ideas/<date>-<slug>.md
  → /speck-ticket         → speck/tickets/0007-<slug>.md   (status: draft)
  → decide against it     → speck cancel 0007 "<reason>"    (status: cancelled,
                            filed in speck/tickets/done/)
  → you edit and approve  → speck set 0007 status ready,     [GATE 1]
                            or Set ready in the panel: commits the ticket
  → speck run             → starts /speck-build for the next ready ticket, one at a time by default,
                            highest priority first, once its after: tickets have shipped
  → /speck-build 0007     → speck start: branch speck/0007-<slug> in its own worktree
       tests from acceptance criteria → implementation → tests pass
       → builder self-check (edge cases, error paths, claims, scope)
       → review loop with an independent reviewer (see below)
       → approved?  yes → logs filled in, status: approved (waits on its branch, no PR),
                          or shipped straight away if auto_ship allows it
                    no, after max rounds → status: blocked + question for you
  → you read `speck pack 0007`
  → /speck-ship 0007      → checks, final test run, ticket set to done and   [GATE 2]
    or Ship in its review pack in the panel: runs the same speck ship
                            filed in speck/tickets/done/, merge into main,
                            push, branch deleted locally and on the remote
```

`speck ship` sets the ticket to `done` on the ticket branch just before merging. Until you ship, `main` is unchanged. `speck ship` refuses, changing nothing, unless the ticket is `approved`, the review loop says `ship`, the working tree is clean, no commit after the reviewer's approval touched files outside `speck/`, and `commands.test` is set and passes (taking a turn, as `speck test` does). The tests run on what would land: the ticket merged with the base branch as it is now, including any new commits on the remote, so a clean merge into a base branch that has moved on ships without another review. When your base branch and the remote's each have commits the other doesn't, ship first merges the remote's into yours with a merge commit, saying in one line which commits it brought in, and keeps that merge even if the ship then fails. It refuses, changing nothing, when they conflict, or when the merge would overwrite uncommitted changes or untracked files where the base branch is checked out, naming those files. What lands is exactly what passed, apart from the ticket's own file, which ship marks done. If you commit to the base branch while the tests run, ship runs them again with your commits, up to three times in all; after catching up with the remote, it refuses instead, as your base branch and the remote's then each have commits the other doesn't. If they fail but the base branch's own tests pass, ship says the failure comes from the ticket's change or, when the base branch has moved on, that the tests failed on the ticket as it would land, because of its own change or because of it with the base branch's newer changes, and to merge the base branch's newer changes into the ticket, fix the failing tests, get it reviewed, then ship again. Either way it names the failing tests when the output is TAP. If the base branch's own tests fail too, ship blames the base branch (exit 14) only when every failing test also fails there, a test counting as failing there only when one of the same name does. Otherwise it says the ticket fails tests that pass on the base branch, names only those and says the base branch is failing as well; an auto-ship then exits 16, so `speck run` hands the ticket back to its build instead of putting shipping on hold. When the merge has conflicts, ship tests the ticket branch alone, then refuses at the merge. Ship reuses a recorded passing result for the same code, as `speck test` does, but never a recorded failure. If its tests stall, ship refuses, saying so, without checking the base branch's tests, and the ticket stays approved to ship again. Uncommitted edits in the base branch's checkout stay there through the merge, unless they're in a file the ticket changes, which refuses at once, or staged: git won't merge over a changed index, so ship says once which files are staged and waits, changing nothing, until they're committed or unstaged. It checks again every few seconds and refuses after `ship_wait_minutes` (default 30). A merge conflict is aborted and leaves everything as it was. If the ticket branch is checked out in another git worktree, ship does the branch steps there and the merge where the base branch is checked out, then removes the ticket's worktree. A ship that was killed while the tests ran on the merge leaves that merge checked out in the ticket's worktree; when that worktree is where `speck start` puts it, the next ship checks the ticket's branch out there again before anything else, or refuses, naming the worktree and saying to run `git checkout <branch>` there, when something else is checked out there or git won't switch. `speck run`'s ship queue tries a ticket whose ship was killed again on its next check, without waiting for a new commit, once until the base branch or the ticket's branch has a new commit. Once it has merged, ship removes the ticket's scratch files, as `speck cancel` does: every file and folder in the temporary folder (`/tmp`, unless `TMPDIR` names another) whose name starts with `speck-<id>-`, such as the build's test output and review prompt. One it can't remove is named in one line and doesn't stop the ship; a ship that refuses leaves them all, since the build may still need them.

## Ticket size rules

A ticket is ready only if it passes all of these. `/speck-ticket` checks them and offers a split when a ticket fails.

| Rule | Limit |
|---|---|
| Outcome | One outcome that you can observe or verify. No "and" joining two outcomes in the title. |
| Acceptance criteria | 1–5, each testable |
| Ticket length | Fits on one screen (about 40 lines of body) |
| Expected change | Reviewable in one sitting. Default guideline is ≤ 300 changed lines, excluding tests and lockfiles (configurable). |
| Size | `S` or `M`. `L` can never be `ready`; it must be split into sibling tickets. |
| Risk | `low` or `high`. `high` means it touches auth, payments, data deletion, migrations, infrastructure or secrets, and makes the reviewer stricter. |

Guardrail during build: if the diff passes the size limit before the tests pass, the builder stops and proposes a split. It doesn't push on.

**Criteria about documents.** A document is any file written for people to read, such as the README, `docs/` and the changelog. A criterion about a document's wording, tone, order or layout ends with `(checked by review)`: the builder writes no test for it, and the reviewer judges it by reading the document as it is now, citing the passage as its evidence, without counting a missing test against it. A criterion about a fact in a document has no marker and is tested: a command, a setting's name, a version, a file name, a link, or a name that mustn't appear. No test may check a document's exact wording, or the order of its sentences, paragraphs or headings: the reviewer blocks a change that adds one, because the next edit to that document would fail the suite and hold up every ship. The skills and the reviewer prompt are instructions to agents rather than documents, so this rule doesn't cover tests of their wording.

## The review loop

The implementation agent owns the loop. It spawns a reviewer subagent and they work in turns until the reviewer approves or the loop escalates to you.

**Roles**

- **Builder:** writes tests and code. It can fix a finding or dispute it with a reason. It cannot approve.
- **Reviewer:** reads the ticket, the diff and the test output. It runs read-only and cannot edit code. It is the only party that can approve.

The reviewer gets a summary of the test output rather than all of it: when the output is TAP, as `node --test` writes it, speck keeps the run's totals, every failing test with its details and every test named with the ticket's id, and says where the full output is. When a full run passed only on its second try (its output ends with a `Flaky:` line), the summary says the run passed, keeps the full run's totals, and lists the tests that failed then passed under "Passed on a second try" rather than as failing tests. Other formats are sent in full. The output is from the test files the builder ran with `speck test --files`, not the whole suite, which runs in `speck ship`: the reviewer judges a criterion that no test that passed before fails from those tests and the change. Each round's record keeps how many failing tests the summary listed and which passed on a second try, and the review pack shows them for the latest round under "Tests", so it agrees with what the reviewer was told. A round given output that isn't TAP, or none, records nothing, and the pack has no "Tests" part.

**Protocol**

1. **Round 1.** The builder spawns the reviewer with the ticket, the diff against the base branch and the test output. The reviewer returns a structured verdict (`templates/review-verdict.schema.json`):
   - a result for each acceptance criterion: `pass`, `fail` or `unclear`, with evidence;
   - findings, each `blocking` or `minor`;
   - a verdict: `approve`, `changes_requested` or `escalate`.
2. **Builder's turn.** The builder answers every blocking finding with one of:
   - `fixed`, with the change made;
   - `disputed`, with a reason;
   - `needs_pm`, for a scope or product question.
3. **Next round.** The builder resumes the *same* reviewer session, so the reviewer remembers its earlier findings, and sends its responses plus the new diff. The reviewer re-checks, accepts or rejects each dispute, and issues a new verdict.
4. **Termination.** The loop ends in one of four ways:
   - **Approve:** no blocking findings and every criterion passes. The ticket waits for you to ship it, or ships straight away if `auto_ship` allows it.
   - **Max rounds reached** (default 3): the ticket becomes `blocked`, with a summary and one specific question for you. Merge rounds don't count towards this limit (see below). If the round at the limit asked for changes but left no more than one blocking finding open, the ticket gets one extra round by itself, without asking you, and blocks only if that round doesn't approve too. An escalation or a repeated disagreement blocks it all the same. The ticket's Review rounds, its review log, its Delivery log and the review pack ("round 4 of 3, an extra round") mark the extra round.
   - **Repeated disagreement:** the same finding is disputed in two consecutive rounds. It escalates to you rather than looping.
   - **`needs_pm`:** the ticket becomes `blocked` with that question.
5. **Minor findings never block.** They're logged in the ticket and offered as new ideas.

**Merge rounds.** When an approved ticket's ship is refused, the builder changes it and gets the change re-reviewed: a merge of the base branch after a conflict, or a fix when the tests fail on it as it would land. A round is a merge round whenever the round before it approved, whether or not the branch merged the base branch in since. The rounds after it, until one approves, re-review the same change, so they're merge rounds too. Merge rounds don't count towards `max_review_rounds`, so a ticket approved in its last allowed round can still have its change checked. They have their own limit instead: `limits.max_merge_rounds` (default 2) merge rounds in a row without an approval block the ticket. The rule on repeated disputes applies to merge rounds as to any other. The ticket's Review rounds, its review log and the review pack mark each merge round.

**Records:** each round is saved in the ticket file itself, in a `## Review rounds` section at the end that only speck writes. Each round is a collapsed `<details>` block with a one-line summary (round, reviewer, verdict, and "merge round" for a merge round) and the full record as a `json` code block, so a ticket is one file holding its whole history, and it moves into `done/` with its rounds. The section is left out of the reviewer's diff and prompt, and `speck lint` reports an error if a round isn't valid JSON or the rounds are out of order. A short summary also goes into the ticket's Review log. The review pack (`speck pack <id>`) is built from the recorded rounds. Working files for a review in progress go in `speck/.cache/`, which git ignores.

**Reviewer adapters**

| Adapter | How it runs | Notes |
|---|---|---|

| `claude` | `claude -p --permission-mode dontAsk --setting-sources= --strict-mcp-config --disallowedTools "Edit Write NotebookEdit" --output-format json`, then the same with `--resume <session>` for later rounds | For any builder: speck runs it, so a Codex or Cursor build can be reviewed by Claude. `dontAsk` runs read-only commands and denies anything else rather than asking, and the file-writing tools are taken away. **Time limit.** A reviewer speck runs, Codex, Claude or a command reviewer, that hasn't finished after `review_timeout_minutes` (in `speck/config.yml`, default 30, a whole number of 1 or more) is ended, with every process it started. The round fails, saying the reviewer took longer than that many minutes, records nothing and leaves the ticket as it was, so it can be run again. A bad value is refused, saying how to fix it, before any reviewer runs. The `claude-subagent` reviewer runs in the builder's own session, so it has no limit.

**Command reviewers.** Set `reviewer: <name>` and give that name a `command` under `reviewer_options`. `{model}` and `{effort}` in the command are filled in from the ticket's `reviewer_model` and `reviewer_effort`. When a value is blank, the placeholder and the flag just before it are dropped, so the reviewer uses its own default. The command runs from the repo root without a shell, gets the round-1 prompt (the same text `speck prompt <id>` prints, schema included) on stdin, and must print the verdict as JSON, in a ```` ```json ```` block, as a JSON object with a `verdict` key among prose (the last such object counts), or in a JSON envelope whose `result` string holds any of these. Later rounds resend the round-1 prompt exactly as it was sent (kept in `speck/.cache/`, or rebuilt from the round-1 commit if that copy is gone), every earlier verdict and builder response in order, then the new response, diff and test output. A non-zero exit, output with no verdict or an invalid verdict is a plain error quoting the last five lines of stderr, and nothing is recorded. speck records the round itself, so the builder never handles the verdict. Read-only is only an instruction in the prompt: speck doesn't sandbox a command reviewer, so pick the tool's own read-only mode in the command. Check each tool's current flags; for example:

```yaml
reviewer: cursor
reviewer_options:
  cursor:
    command: "agent -p --mode ask --trust --output-format json --model {model}"
```

**Resuming a command reviewer.** With `session_id_path` set, speck saves the session id from each round's output as `thread_id`. With `resume_command` (containing `{session}`) as well, later rounds continue that session with only the new round's prompt, as Codex does. If there's no saved id, no `resume_command`, or the resume exits non-zero, speck falls back to a fresh run with the full history and says why in one line. The review pack marks each round as a continued or fresh session.

Config rejects a `builder` and `reviewer` from the same family unless `builder_model` and the reviewer's model are both set and differ, or `allow_same_model_review: true` is set. `builder_model` counts for Codex and Cursor builds only when `build_command` is blank, so speck starts them itself. A Cursor build with `builder_model` blank runs on Cursor's `auto`, which counts as a model of its own, so a Cursor reviewer with any model but `auto` is accepted.

**Reviewer model and effort.** `reviewer_model` and `reviewer_effort` in `speck/config.yml` set the reviewer's model and effort level for the whole repo. `speck new` leaves them blank in each ticket, as it does `builder` and `reviewer`, and a value on the ticket overrides config. A blank ticket value falls back to the settings when the build starts and when each review round starts, so changing a setting reaches every ticket that doesn't name its own. A review round whose reviewer or model differs from the last round's starts a fresh session with the full history. If both are blank, speck sets nothing: Codex uses its own default, and a `claude-subagent` reviewer runs on the builder's model in a fresh session. Model names are free text in the reviewer's own format and aren't checked. Effort must be blank, one of `low`, `medium`, `high`, `xhigh` or `max`, or an effort that `codex debug models` lists for one of Codex's models, such as `ultra`. Codex gets them as `-m` and `model_reasoning_effort` in every round, a `claude` reviewer as `--model` and `--effort`, and a `cursor` reviewer as `--model` only. The review skill passes them to the subagent (`speck reviewer-settings <id>` prints them). Every saved round and the review pack show the model and effort used, or "default".

**Builder model.** `builder_model` in `speck/config.yml` sets the model every build `speck run` starts, resumes or hands back runs on. With `builder: claude`, speck adds `--model <value>` to `build_command`, in place of any `--model` it already has: Claude Code takes `fable`, `opus`, `sonnet` or `haiku` for the newest model of that kind, or a full model name. Blank leaves the command as it is, so the builder uses its own default. With `builder: codex` and `build_command` blank, speck builds with its own Codex command (see Codex builds below) and passes it as `-m <value>`. With `builder: cursor` and `build_command` blank, speck builds with its own Cursor command (see Cursor builds below) and passes it as `--model <value>`, or `--model auto` when it's blank. Other builders aren't given it yet: with `builder_model` set, `speck run` says so in one line when it starts.

**Codex builds.** With `builder: codex` and `build_command` blank, `speck run` starts each build as `codex exec --json --dangerously-bypass-approvals-and-sandbox '$speck-build <id>'`. Codex chooses its own session id, so `speck run` reads it from the first `thread.started` line of the build's log and keeps it in the build's run record. A killed build it resumes and a hand-back carry on that session with `codex exec resume <session> --json --dangerously-bypass-approvals-and-sandbox '<message>'`. A build that stopped before Codex wrote its session id can't be resumed: `speck run` says so in one line, as for any build it can't resume. Unless `resume_command` is set to something other than Claude Code's, the panel and `speck status` show `codex exec resume` as the command that reopens a Codex build's session. A `build_command` that's set is used as it is. A build you start yourself with `/speck-build` runs on your session's own model.

**Cursor builds.** With `builder: cursor` and `build_command` blank, `speck run` first makes a chat for each build with `agent create-chat`, and keeps the id it prints as the build's session. It then starts the build in that chat as `agent -p --force --trust --output-format stream-json --resume <session> '/speck-build <id>'`, with `--model <builder_model>`. A blank `builder_model` is passed as `--model auto`, the only model a free Cursor plan can use, as a chat keeps the model it first ran on. When `agent create-chat` fails, `speck run` doesn't start the build: it says why in one line, leaves the ticket ready and tries again on its next check. A killed build it resumes and a hand-back carry on the chat with `agent -p --force --trust --output-format stream-json --resume <session> '<message>'`. speck finds Cursor's CLI as `agent`, or as `cursor-agent` when only that is installed. Unless `resume_command` is set to something other than Claude Code's, the panel and `speck status` show that command as the one that reopens a Cursor build's chat. A `build_command` that's set is used as it is.

**Each ticket's own builder.** With `build_command` blank, or exactly Claude Code's own command as switching the builder to Claude Code sets it, `speck run` builds each ticket with the builder its `builder:` field records, or the one in `speck/config.yml` when it records none: Codex's or Cursor's own command above, or, for `claude`, the `build_command` speck sets up for Claude Code. `builder_model` is passed only when the ticket's builder is the one in `speck/config.yml`, as it's in that builder's own format. A ticket whose builder isn't installed, or that speck has no command of its own for, isn't started: `speck run` says why in one line, the Foreman's detail shows it, and it leaves the ticket ready and tries again on its next check. A killed build it resumes and a hand-back carry on with the agent the build started with. When `build_command` is any other command, one you've written yourself, every build uses it, the Settings view says so, and if a ticket records a builder other than the one in `speck/config.yml`, `speck run` says once as it starts that tickets' own builders are ignored.

## Repo layout (in a project that uses speck)

```
AGENTS.md / CLAUDE.md        # points agents at speck's tickets and rules
speck/
  config.yml                 # test command, limits, base branch, how tickets ship, and the defaults for your own settings
  ideas/                     # low-ceremony notes and captured conversations
  ideas/done/                # ticketed notes, filed away under the same name
  tickets/0007-<slug>.md     # numbered tickets; status lives in frontmatter, review rounds at the end
  tickets/done/0001-<slug>.md # closed tickets (done or cancelled), filed away under the same name
  .cache/                    # working files for reviews in progress (ignored by git)
.claude/skills/speck-*/      # skills for Claude Code
.agents/skills/speck-*/      # the same skills for Codex, cptr and other agents
.speck/                      # the speck command and templates
```

Every ticket opens with a header rendered from its frontmatter, such as `# 0007 · <title>` followed by `**Status:** 🔍 reviewing`, so previews that hide frontmatter still show the title and status. speck rewrites it whenever it changes the title or status, and `speck lint` warns if it's missing or stale.

Tickets are committed and often published, so you can list words you'd rather keep out of them, such as your real name or an old alias, in `~/.config/speck/private-words` in your home folder: one word per line, with blank lines and lines starting with `#` skipped. `speck lint` then reports a ✗ for each line of a ticket that contains one of them, ignoring case, so `speck set <id> status ready` refuses it. The error names the line but not the word. Without the file, lint checks nothing for it; a file it can't read gets a ! warning. The file lives outside the repo, so the list itself is never committed.

`speck/tickets/` holds only work in progress; `speck/tickets/done/` holds closed tickets, which means `done` or `cancelled`. Setting a ticket to `done` moves its file into `speck/tickets/done/` under the same name, `speck cancel <id> "<reason>"` sets it to `cancelled` with the reason and the date it was cancelled recorded in the ticket, and any other status moves it back into `speck/tickets/`. Commands take a ticket id, not a path, so they find it in either folder, and re-running `speck init` files any done ticket left behind by an older version. A move never overwrites: if the same file name is already in the other folder, speck stops and asks you to keep one.

Idea notes are filed the same way. `speck new --source=speck/ideas/<file>.md` sets the note to `ticketed (<id>)` and moves it into `speck/ideas/done/` under the same name, and the ticket's `source:` points there. Later tickets from the same idea take it from `speck/ideas/done/` (the old path still finds it), and re-running `speck init` files any ticketed note left in `speck/ideas/` and updates the tickets that point at it. So `speck/ideas/` holds only ideas still waiting to be shaped.

| `speck test` | Runs `commands.test` in this checkout and exits with its exit code. A later `speck test` on the same files with the same test command prints that result, saying which commit it's from and when, and exits with its exit code without running the suite. So does a run that waited for a turn when such a result was recorded while it waited: once its turn comes, it frees the turn at once and prints that result instead. `speck test --fresh` always runs it. A full run that fails with an exit code, in `speck test` or `speck ship`, runs `commands.test_files` once more with just the files of its failing tests, read from each one's `location:` in TAP output. If that run passes and every test that failed passes in it, the full run counts as passed (and is recorded as a pass): its output ends with a line `Flaky: <test>; <test>…`, and those tests are added, with the time and the branch, to `speck/.cache/flaky/flaky.log` in the main checkout, which every worktree shares. Otherwise it fails as before, its output being both runs' in turn. A failing test that also failed in the result recorded for the base branch's latest commit (the same name, in a file at the same path) is left out of that second run, and so is its file unless a test that didn't fail there failed in it too. A line names the tests left out. When that leaves nothing to run, there's no second run, and the line says the failing tests already fail on the base branch. With any test left out, the full run fails whatever the second run does, and has no `Flaky:` line. There's no second run when `commands.test_files` is blank or has no `{files}`, when a failing test has no `location:` in a file in the repo, or when the run stalled or was stopped. `speck test --files <file>…` runs only those files with `commands.test_files` (`{files}` stands for them), from the repo root, taking a turn as a full run does, without a recorded result; when that's blank, it says so in one line and runs the whole suite instead. `commands.checks` lists quick test files that check rules for the whole repo, such as a limit on a script's length, so a build that breaks one finds out before review rather than at ship. Write them separated by spaces or commas, as `speck config set commands.checks "<file> <file>"` does, or as a list in brackets. `speck test --files` runs them in the same run as the files it's given, each file once, and fails as it would for a failing test in those files. Before anything runs, it checks each one is a file, and when one isn't, it fails naming it and runs nothing, whether `commands.test_files` is set or blank. When `commands.checks` is blank, `speck test --files` runs only the files it's given. `speck test --recorded` prints the result recorded for this checkout's code and test command, as `speck test` does when it reuses one, and exits with its exit code, without running any tests. With none recorded, it runs nothing, says so in one line and exits with code 0. A build doesn't run the whole suite before it starts: before it changes anything, it lists the tests already failing from `speck test --recorded`, writing `Failing before this build:` in the ticket's Notes with the failing tests, `none`, or `not checked` when no result is recorded, which the reviewer treats as listing no tests. After that it runs only test files: the ticket's own while it checks that they fail and fixes until they pass, and, before every review round (merge rounds included), the ticket's own test files, any existing test files it changed and the files of any test that failed in its last test run, with `commands.checks` running alongside them. The whole suite runs in `speck ship`, not during a build: `speck ship` always runs it, on the ticket as it would land. |
| `/speck-build <id>` | Takes a `ready` ticket: `speck start`, then in its worktree: tests from acceptance criteria, implementation, then the review loop. Before each review round it runs only the ticket's test files with `speck test --files`, saying in the round's response file which ones: the whole suite runs in `speck ship`, not during a build. Ends at `approved`, with no PR: `speck run`'s ship queue ships it when `auto_ship` covers it, and you ship the rest. When a ship the queue started hits a conflict (exit 13), `speck run` resumes the build's session, which merges the base branch in, resolves each file by its `speck merge-check` class (both sides' added lines kept, lockfiles rebuilt with the project's install command, logic changes keeping the intent of both sides), runs the ticket's test files and gets the merge a merge round before the queue ships it again, and the same when the tests fail on the ticket as it would land, merged with the base branch, while the base branch's own pass, or while it's failing but those tests pass there (exit 16), whether its own change broke them or the base branch's newer changes did, running the failing tests' files and the ticket's own. After two such hand-backs without shipping, it blocks the ticket instead. When the base branch's own tests fail (exit 14), it changes no code, creates one fix ticket unless an open one covers it, sets it ready unless it's already on its way, and stops, leaving its own ticket `approved`. It asks the user only when two tickets contradict each other or a merge round blocks. |
| `/speck-review <id>` | Runs the review loop on its own (for example, after a manual fix) |
| `/speck-ship <id>` | Your gate. Runs `speck ship <id>`: checks, marks the ticket done, merges into the base branch, pushes and deletes the branch. Only you start it; in Claude Code the skill can't be started by the agent. The Ship button in an approved ticket's review pack in the panel does the same: it asks first, then runs `speck ship <id>`, showing that the ticket is shipping until it finishes, and its message if it refuses. With `auto_ship` on, `speck run`'s ship queue runs `speck ship <id> --auto` for each approved ticket it covers. A document task ships only this way, never by itself. Its document is in `outputs/`, outside git, so `speck ship` runs no tests for it and merges only its ticket's own records, refusing one whose branch changes any file outside `speck/` and naming those files. While one `speck ship` runs for a ticket, another for the same ticket refuses, changing nothing. A ship that merges but can't push the base branch, whoever started it, shows the ticket in the panel's Shipped list with "Merged, but not pushed" and `speck ship`'s message, and `speck status --json` gives it in the ticket's `ship`, until git sees the commit on the remote. |
| `/speck-status` | Lists tickets by status: approved (waiting for you) first, then blocked with their questions, then cancelled with their reasons |

Agents never merge or ship unless the user runs `/speck-ship` or clicks the panel's Ship button. Shipping pushes the base branch directly, so it mustn't be protected by a "require a pull request" rule, unless `ship_mode` is `pr`, when shipping merges each ticket's pull request on GitHub instead and pushes nothing straight to the base branch.

## Releases

`main` moves with every ship, so it's whatever shipped last. Releases are tagged versions (`v0.3.0`), and the README always points at the latest release, so anyone following its setup prompt gets a release rather than `main`. The setup prompt runs `npx 'github:luroai/speck#semver:*' init`, quoted so the `*` works in zsh as well as bash, and every other install command does the same. npm resolves it to the highest version tag, so the setup prompt always installs the newest release tag and a release ticket no longer changes it.

A release is an ordinary ticket. It sets the version in `package.json` and adds the release's section at the top of `CHANGELOG.md`. The version check covers `package.json` and the newest section of `CHANGELOG.md`: a test fails if they don't name the same version. The maintainer ships the release ticket, as shipping is theirs. When a release ticket lands on `main`, a workflow tags the version and publishes its GitHub release from `docs/releases/v<version>.md`, so a release ticket must add that file. Until the workflow has run, the setup prompt still installs the release before it.

## Where it's heading

speck runs on your own machine today: the panel is a local page over your repo, and builds run in worktrees beside your checkout. That suits people comfortable with a local setup, and it keeps everything in the repo with no service to trust.

A hosted version, where the repo lives on GitHub, builds run in the cloud and the panel is a page you sign in to, would suit people who don't want a development setup at all. It's a bigger, deliberate step, not something to grow ticket by ticket. A hosted page that drives builds on someone's own machine is ruled out: it would be a remote-control channel into a machine where builds skip permission prompts.

Not yet:
- Windows (speck says so plainly and suggests WSL);
- Jira or GitHub Issues sync;
- dependency graphs beyond each ticket's `after:` list;
- hosted or cloud builds.

## Success measures

- ✅ speck builds itself: its features go through its own tickets, builds and reviews.
- ✅ At least 20 tickets shipped through speck, with published actuals: 104 by 11 October 2026, with a median of 12 minutes and 2 review rounds each (see the README).
- Someone other than the maintainer installs it and ships a ticket.
